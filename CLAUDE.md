# tela-zen — working notes for Claude

A Zen Browser (Firefox 154 base) fork built with `surfer`. This file is the
operational knowledge that is easy to lose between sessions and expensive to
rediscover. Design intent lives in the Zen upstream docs; this is about the
traps.

## Layout

```
src/zen/**              our changes; each file is SYMLINKED into engine/zen/**
engine/                 the Firefox/Zen source tree (patched)
prefs/**/*.yaml         shipped default prefs
PKGBUILD                packages engine/obj-*/dist/zen-*.tar.xz
tela-zen.install        pacman hook: clears stale startup caches
```

Build chrome JS/CSS: `cd engine && ./mach build faster` (~2s).
Package: `npm run package && makepkg -f`. Install needs the user's password.

## Things that will bite you

**A stale startup cache makes an install look like it did nothing.** This cost
an entire session. Gecko validates its compiled-chrome cache against `BuildID`,
which is compiled into libxul at configure time and is *not* regenerated by
`mach build faster`. Every package therefore ships the same BuildID, so a
long-lived profile keeps executing previously compiled chrome JS after every
install and restart — looking current, behaving old. `tela-zen.install` now
clears `~/.cache/zen/*/startupCache` on install/upgrade. If a change still
seems to do nothing, verify the code is actually *loaded* before theorising:

```
typeof window.gZenSidebarResults   // in the running window, via Marionette
```

**A fresh test profile cannot reproduce a stale-cache bug.** Copies of the
user's profile made with rsync exclude `startupCache`, so they compile fresh
and always work. Comparing "works in my test window, fails in theirs" then
reads as a mysterious profile difference when it is only cache age. To
reproduce, copy `~/.cache/zen/<profile>/startupCache` into the test profile.

**Debug the *running* window, not a copy.** Relaunch with
`--marionette -remote-allow-system-access` and drive chrome-context JS over
port 2828 (`<len>:<json>` framing; `Marionette:SetContext` → `chrome`).
Importing a module manually there bypasses the normal loader, so it proves the
module works but *not* that it loads — check both.

**`ZenPreloadedScripts.js` loads modules in a loop.** It used to have no error
handling, so one throwing module silently dropped every entry after it; ours
was last and never loaded. Each import is now wrapped in try/catch. Anything
appended to that list is the first casualty of an unrelated throw.

**`npm run import` is broken** on an already-applied
`toolkit/components/pictureinpicture/PictureInPicture.sys.mjs` patch. Folder
patches (the `src/zen` symlinks) are applied *before* the git patches, so a
partial run still copies zen files. A NEW file under `src/zen` needs its
symlink created by hand in `engine/zen/**`, or `config.status` fails with
"File listed in FINAL_TARGET_FILES does not exist".

**The urlbar popup and the results list are the same switch.** Stock CSS hides
the view with `.urlbar:not([breakout])`, and `#openPanel` *is* the floating
popup machinery. Disabling breakout to stop the popup also kills results.
`ZenSidebarResults.sys.mjs` therefore renders its own list in the sidebar's
normal flow and subscribes to `gURLBar.controller.addListener(...)` — it never
touches `.urlbarView` or `[breakout]`.

**Sidebar width has two mechanisms.** `vertical-tabs.css` pins *both*
`min-width` and `max-width` with `!important`, and `min-width` beats `width`
regardless of `!important`. Expanded sidebars (`zen-sidebar-expanded="true"`)
size from an inline width Zen sets in JS; collapsed ones size from
`--zen-toolbox-max-width`. A width fix that ignores either mode does nothing.

**`toggleAttribute(name, true)` sets an empty value.** `#urlbar[focused="true"]`
never matches; use `[focused]`.

**`npm run import` was broken by a patch-ordering collision** (fixed 2026-09-08,
not yet re-run end to end). Two patches touch
`toolkit/components/pictureinpicture/PictureInPicture.sys.mjs` — ours and
`external-patches/firefox/issue_14710.patch` — and each applied cleanly to
pristine upstream but not after the other. Surfer applies ours first, so the
external one failed and took the whole import with it. Regenerated the external
patch against pristine+ours; the result is byte-identical to what the engine
already has. `scripts/regress.py` now validates every `src/**/*.patch` before
launching anything, so this class of rot is visible rather than silent.

**`newProxyInfo()` has no username/password parameters.** Its signature here is
`(type, host, port, aProxyAuthorizationHeader, aConnectionIsolationKey, flags,
failoverTimeout, failoverProxy)`, so SOCKS credentials passed as arguments 4 and
5 compile cleanly, never reach tor, and every container silently shares one
circuit. `newProxyInfoWithAuth()` is the one that sets SOCKS auth.

**A new file needs its jar entry AND a touched jar manifest.** `npm run build:ui`
does not notice a newly *added* line in a `jar.inc.mn` - the entry and the
`ZenPreloadedScripts.js` line were both correct and the file was still absent
from `dist/`, so `gZenCardStack` was `undefined` and every caller threw. Touch
the manifest and rebuild, then check `dist/` rather than trusting a green build.

**A JSON-valued pref default needs the generator fixed, not quoting.** ffprefs
emitted a value raw unless it contained letters, a space or a quote, so `{}`
and `[]` came out as bare literals - illegal in a pref file, and they kill
every pref after them. The yaml worked around it as `value: '"{}"'`, which
shipped the quotes *inside* the string: `Object.keys` on it yielded `0` and
`1`, and the PiP toggle position matched neither "left" nor "right".
`get_value` now quotes everything that is not `true`, `false` or an integer,
which is all `pref()` accepts.

**SASS cannot round-trip most of this tree's CSS.** `src/**/*.scss` compiles to
the sibling `.css` the jar and the symlinks already point at, and `npm run
styles` runs ahead of every build through an npm `pre` hook. But dart-sass
rejects `@media -moz-pref(...)` unless every operand is parenthesised, cannot
emit a `%include` line at all, and - the real blocker - **flattens CSS-native
nesting**, turning `&`'s `:is(<parent list>)` into one selector per branch.
That changes specificity wherever the branches are unevenly specific, which
they are in 38 places across 12 sheets. So a sheet may only become `.scss`
when it has no `&` and no `%include`; ten qualify today. `docs/sass.md` has the
measurements, and `scripts/css_equiv.py` proves a conversion by comparing the
old and new text through Gecko's own parser - a textual diff proves nothing,
since SASS reformats freely.

**`#urlbar` is `position: fixed` in the top layer, at its *static* position.**
`popover=manual` is open the whole time, so a percentage width resolves against
the viewport and `width: auto` is shrink-to-fit, not a fill of the box beneath
it - both have been mistaken for a broken layout. Its resting place in the
horizontal layout is therefore set with explicit `left`/`top` in viewport
terms rather than left to the toolbar row: the row overflows at narrow widths,
and anything that derives the field's position from where the row happened to
put the slot is silently wrong the moment it does. The focus glide is one
`translate` and nothing else. `ZenSidebarResults` now bails out of horizontal
in one place (`_horizontal`), because every width it computes comes from a
sidebar that layout does not have: it held a 181px field inside a 320px slot,
and its focus widen opened an empty 460px band down the window and shoved the
page aside. Guard the whole path, not the entry point - the widen is applied
from a callback two `requestAnimationFrame`s later - and assert the toolbox
width **per frame**, since a widen that reverts inside the transition matches
at both endpoints and still looks exactly like the bug. `--zen-urlbar-wide` is
the durable proof: `_anchorWide` writes it and nothing removes it, so its
presence after a launch says the widen ran even if you could not watch the
frames it ran in.

**Firefox focuses the address bar on the startup blank tab at ~+70ms**, in
every layout, and nothing here can connect in time to see it: Marionette's
`WebDriver:NewSession` takes 1.4-3.3s, and a sampler that starts then reports
`focused: false` and looks like proof of the opposite. It is not. Test a
*cold* start - the preset in the profile's `user.js` - because applying the
preset after launch never reproduces it. That focus used to reach the sidebar
widen and, once the lift existed, opened the browser with the field sailing
into the middle of the window. `_suppressStartupFocus` is the cure and now
runs in every mode, armed at `MozBeforeInitialXULLayout`; from `_setup` it was
both gated on sidebar mode and a paint too late. It publishes
`zen-startup-settling` while it holds, which is what the lift's CSS gates on -
`zen-before-loaded` does not work for this, since `ZenStartup` drops it at
`MozBeforeInitialXULLayout` whenever the watermark is off (the default),
248ms before first paint.

**Most chrome cannot paint over a page, and Marionette cannot tell you which
can.** Remote content composites above `:root`, `#zen-main-app-wrapper` and
even `#browser`; of ten hosts measured only `#zen-appcontent-wrapper`,
`#navigator-toolbox`, `#tabbrowser-tabpanels` and `#tabbrowser-tabbox` put a
pseudo-element over the page. `WebDriver:TakeScreenshot` composites chrome and
page separately, so it answers this question wrongly and *inconsistently* -
the same rule read both ways on consecutive runs. Use `grim -g` aimed from
`hyprctl clients -j` (match on the test browser's own pid) instead. And
`backdrop-filter` on such an overlay renders the backdrop black rather than
blurring it: the page went from 186 to 3 mean luminance.

## Verifying chrome changes

`python3 scripts/regress.py` — launches a throwaway profile, drives Marionette
and checks the things that have broken repeatedly: sidebar urlbar geometry,
layout switching, the right rail actually *painting*, the centred urlbar's
return, presets order and cycle, the card stack, chrome errors, and Tor routing
with its leak assertion. `--only <substring>` narrows, `--keep` leaves the
browser up. Run it after touching chrome JS or CSS; it found four issues on its
first run, two of them real.

`python3 scripts/drive.py` — when a bug only appears under a real pointer.
Copies a real profile (the original is only read), launches the built browser
against the copy with its extensions and logins intact, and records every popup
open/close *with the stack of whoever closed it* plus the sidebar's position.
`--dump <trace.json>` reads it back. It holds the Marionette session open on
purpose: **the browser shuts down cleanly when that client disconnects**, which
killed four hand-offs in a row and read exactly like the user closing the
window. A compact-mode sidebar that slid out from under an extension's
permission prompt survived every synthetic reproduction and appeared on the
first human attempt.

Two lessons already baked into it. A check must assert *painting*, not just
geometry — the rail was laid out and hit-testable while drawing nothing. And a
failing check is as likely to be a wrong assertion as a bug: two of those four
were mine (`cycle` is deliberately `order` minus unconfigured slots, and a
JavaScript **warning** is not an error).

## Testing habits

- `pkill -f <pattern>` matches the shell running it (exit 144). Find the PID
  via `pgrep -x zen` and check `/proc/<pid>/cmdline`, then `kill -TERM`.
- **`until ! pgrep -f "<pattern>"; do ...` deadlocks on itself** — the waiting
  shell's own command line contains the pattern, so the condition never goes
  false. Six background jobs sat forever on this in one session. Check once and
  proceed, or match on something the guard cannot itself contain.
- Never kill or restart the user's browser. Give them a script to run.
- Launch test windows on a spare workspace
  (`hyprctl dispatch movetoworkspacesilent 9,pid:<pid>`). Test windows restored
  from a copy of the user's session look identical to their own window, and
  screenshots have been misattributed more than once because of it.
- An unfocused test window fires `blur` immediately, which hides focus-driven
  UI. Focus-triggered behaviour cannot be verified this way — ask for a look.
- Check `/var/log/pacman.log` for the real install time and compare it against
  the browser's process start time before concluding "they didn't restart".

**`mach build faster` caches jar manifests.** A NEW entry in a `jar.inc.mn` is
ignored until the manifest's mtime changes: the file never lands in `dist/`, and
the `chrome://` URL fails to resolve with no error logged anywhere. Editing an
existing entry is picked up fine, which makes it look like the file is broken
rather than unpackaged. `touch` the manifest and rebuild.

**A malformed pref value silently kills every pref after it.** The prefs yaml
emits values verbatim, so `value: "{}"` became `pref("...", {})` in the
generated `zen.js` — not a legal pref literal. Firefox stops parsing the file
at that line: 113 later prefs, urlbar and layout among them, simply did not
exist, which looks exactly like broken code rather than missing config. The
log line is a single `prefs parse error: unexpected character`, easy to scroll
past. Write a string default as `value: '"{}"'`. Check
`dist/bin/browser/defaults/preferences/firefox.js` when prefs seem ignored.

**`#urlbar-container` has two competing widths.** Zen sizes it with
`calc(var(--urlbar-width) + ...)`, but that variable is set on `#urlbar` — the
*child* — so it only resolves when something else defines it upstream. When it
does not, the container silently falls back to flex and roughly doubles, and
the flip is sticky. Anything that animates the field home must target a width
pinned by our own rule, or it lands on whichever of the two was live.

**`mach package` leaves an `omni.ja` that shadows every later `build faster`.**
Chrome is then loaded from that archive, not from the loose files in
`dist/bin`, so incremental edits appear to have no effect — the file on disk is
current, `chrome://` even resolves to it, yet the running object is old. Delete
`dist/bin/browser/omni.ja` after packaging, or test against the packaged build
deliberately. This cost hours of chasing a "stale build" that was not stale.

**Marionette's port 2828 belongs to whoever binds it first.** A forgotten test
window keeps answering long after you launch a new one, so probes silently
report the old window's state. Kill by matching the profile path
(`grep -q "scratchpad/tf"` over `/proc/<pid>/cmdline`) before every run, and
never `pkill -f zen` — that matches the user's own browser.

**`Preferences.addAll` throws on the first duplicate id and drops the rest.**
Firefox registers some prefs itself (`preferences/config/tabs-browsing.mjs`
owns `media.videocontrols.picture-in-picture.video-toggle.enabled`), so adding
one again threw out of the array and silently unregistered every Zen pref
listed after it — controls then render unbound, showing a checkbox's default
rather than the pref. `zen-settings.js` now filters the list through
`Preferences.get` first. A `preference=` attribute resolves an already
registered pref fine; it only needs adding when nothing else owns it.

**A ResizeObserver callback that returns early DROPS those entries.** Nothing
redelivers them when the condition clears, so a guard meant to skip a few
animation frames froze the tab strip until the next unrelated resize. Worse,
`onPinnedTabsResize` and `getAndApplySidebarWidth` are *also* the explicit
"lay the strip out again" entry points — a tab drop goes through
`updateTabsContainers()` — so guarding them by attribute alone made drops move
the tab in the model and nowhere on screen. Guard only the observer-driven
call (`typeof forAnimation !== "boolean"`, or `Array.isArray(event)`), and
replay the skipped work when the flag clears. `zen-sidebar-animating` is held
for as long as the urlbar keeps focus, so it also needs a watchdog: a blur lost
to a closed window used to wedge it for the session.

**The urlbar widen pins the sidebar with `min-width` AND `max-width`
`!important`.** Anything that leaves that pin behind holds the sidebar at that
exact width and the splitter silently refuses to move. It only ever came off in
`_release`'s 420 ms timer, so a blur lost to a closed window or a re-`_suspend`
wedged the sidebar wide for the session. It now comes off three ways: settling
the animation, the idle `_measureRest` sweep whenever a pin survives at rest,
and a `mousedown` on `#zen-sidebar-splitter` — a drag always outranks an
animation of ours.

**A `chrome:` new tab page is refused by the content process.** Setting
`AboutNewTab.newTabURL` to one resolves, then `AboutNewTabRedirector` fails to
open a channel (`NS_ERROR_NOT_AVAILABLE`) and the tab settles on `about:blank`
— a blank page, no error in the UI. Zen's own empty tab escaped it only because
`addTrustedTab` loads with the system principal. `ZenStartup` now marks the
tabs opened *for* the new tab page and reloads them with that principal;
Gecko moves the browser back to the parent process on that load. Note
`addTab` fires `TabOpen` synchronously, before it returns the tab, so the
redirect is queued off `dispatchToMainThread` rather than hung on that event.

**`loadFrameScript("chrome://…")` silently fails in a loose `build faster`
build.** `dist/bin/.../zen-components/*.js` are symlinks into `src/`, and the
content sandbox refuses to read them — "Error opening input stream (invalid
filename?)", logged nowhere. The frame script is then simply absent while
`getDelayedFrameScripts()` still lists it, so every event a page dispatches
vanishes and it looks exactly like a broken sanitiser. Launch test instances
with `MOZ_DISABLE_CONTENT_SANDBOX=1`; a packaged build is unaffected.

**Marionette's port is first-come, first-served.** Several test browsers at
once means `--marionette` binds 2828 for whoever launched first, and every
later probe silently drives *that* window. This produced a string of
impossible readings — edits that "did not land", a preset that "regressed" —
all of them measurements of somebody else's browser. Pin
`user_pref("marionette.port", <your own>)` in the test profile and assert the
log says that port before trusting a single number.

**XUL `flex="1"` is a UA-origin `!important` declaration.** `#zen-main-app-wrapper`
carries it, and author CSS cannot beat it — `flex: 0 0 auto !important`, and even
an inline `flex-grow: 0 !important`, still compute back to `1 1 0%`. That is why
`#browser` kept claiming half the window in customize mode while its content area
was hidden, and why the empty region looked like a stray `customization-target`
when it was really the toolbox row's slack. The attribute has to be *removed*,
not overridden.

**Marionette refuses a second connection while a session is live.** A client that
exits without `WebDriver:DeleteSession` wedges the port until the browser
restarts, and the next connect fails with ECONNREFUSED — which reads exactly like
the browser having died. Combined with the first-come-first-served port, this
accounts for most "the browser is gone" confusion in a multi-agent session.

**Marionette's content context follows its own window handle**, not
`gBrowser.selectedTab`. A tab opened with `gBrowser.addTab` is invisible to it —
`document.getElementById` in content returns null against the *original* tab, not
the one on screen. Navigate the driven tab with `WebDriver:Navigate` instead.
Related: an untrusted `requestFullscreen()` needs
`full-screen-api.allow-trusted-requests-only` false; a synthesized
`WebDriver:ElementClick` does not count as user activation.

**Upstream collapses `#navigator-toolbox` and every `<toolbar>` in fullscreen**
(`tabbrowser/fullscreen-and-pointerlock.css`), and nothing else. Our
`#zen-horizontal-chrome` is neither, so it painted a 77px band over fullscreen
video in the horizontal and shy presets. Any new chrome container of ours needs
its own `:root[inDOMFullscreen]` rule — or to be a real `<toolbar>`, which is why
`#zen-right-rail` never had the bug.

**`locales/**` is copied into `engine/`, not symlinked.** Every JS and CSS file
under `src/` is a symlink, so an edit is live immediately — FTL is the
exception. An FTL change is invisible to the browser until `npm run l10n:zen`
runs, which reads exactly like a string that "did nothing".

**Wayland will not map a popup that no user input opened**, so `grim`
photographs an empty window. `openPopupAtScreen` high on the screen does map —
that is how panels and menus get screenshotted here. Marionette's own screenshot
misses popup surfaces entirely, and X11 under Xvfb is not an option: the build
crashes there.

**A XUL `<panel>` does not scroll; a `<menupopup>` does.** Gecko clamps both to
the screen, but `arrowscrollbox` only rescues the menu — a clamped panel simply
cuts its content off with nothing to grab. Any panel taller than ~250px needs
`overflow-y: auto` on its body. The failing anchor band is the *middle* of the
screen, not the bottom: a low anchor flips the panel upward and it fits.

**Gecko does not know where the compositor put it under Wayland.** It reports
the window at 0,0 and popups at fictional screen coordinates, so `grim -g` aimed
from `panel.screenX/screenY` photographs the wrong place — shoot the whole
output instead. `hyprctl keyword` and `dispatch <name> <args>` are also gone in
Hyprland 0.56 (Lua `hl.dsp.*`), so window geometry cannot be pinned that way.
To force a clamped popup, set `layout.css.devPixelsPerPx` high rather than
moving the window — a real HiDPI condition, not a rig.
